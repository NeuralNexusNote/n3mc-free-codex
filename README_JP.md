# N3MemoryCore Free Codex版 v1.9.1

Codexの会話を検索できる形でPCに保存します。2つのフックを信頼すると、発言の保存前に関連記録を呼び戻し、ターンの終了時に応答を保存します。SQLiteとローカル埋め込みを使い、チャットやプロジェクトをまたいで使えます。

[English](README.md) · [日本語の実装指示書](N3MemoryCore_v1.9.1_Free_JP.md)

## 仕組み

```
ユーザーの発言
    │
    ▼
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  1. 自動保存  │────▶│  2. 意味検索  │────▶│ 3. コンテキスト│
│  前回の回答を │     │  関連する過去 │     │    注入       │
│  DBに保存    │     │  の記憶を取得 │     │  Codexに渡す │
└──────────────┘     └──────────────┘     └──────────────┘
                                                 │
                                                 ▼
                                          Codexが過去の
                                          文脈を踏まえて回答
```

Codexのフック機能を利用し、すべて自動で行われます。ユーザーが意識する必要はありません。

- **保存するもの** — あなたの発言と Codex の返答を、すべてそのまま保存します。コードブロック（``` で囲んだ部分）は `[code omitted]` として保存します。N3MC が覚えるのは、話したことと決めたことです。コードは、プロジェクトのファイルにあります。Codex 自身が差し込む入力（タスクの通知、エージェントのメッセージ、システムの注意書き）は保存しません。
- **呼び出すもの** — 発言のたびに、フックが記憶を検索します。関係のある記録を、Codex があなたの発言を読む前に、コンテキストに加えます。

### 3 つの場面

> **月曜** — Codex と相談して、サイトのデータベースを PostgreSQL にすると決めます。理由も話します。
>
> **水曜** — 新しいセッションで、「データベースは何にしたか」と聞きます。月曜の決定と理由が、質問と一緒に Codex に届きます。説明し直す必要はありません。
>
> **金曜** — 別のフォルダで作業しています。その話題になると、月曜の決定がここでも呼び出されます。Free は、すべてのプロジェクトのフォルダで 1 つの記憶を使います。

### 実際に Codex に届くもの

水曜の質問のときに、フックが加えた塊です。フックを実際に動かして取ったものです（一時的なデータフォルダを使い、2 つ目のセッションは 1 つ目と別のフォルダで始めました）。

```text
# Recalled Memory Context
Search query: サイトのデータベースは、何にすると決めましたか。理由も教えてください。

## Top matches (use these to answer the question)

_If several versions of the same content appear, the one with the newest `saved` time is the current one._

## [1] score=0.5472 saved=2026-11-22 15:59 (UTC+0900) claude-code
[user] サイトのデータベースは PostgreSQL にしましょう。複数の人が同時に編集する予定で、SQLite は書き込みのたびにファイル全体をロックするからです。

## [2] score=0.4779 saved=2026-11-22 15:59 (UTC+0900) claude-code
[claude] 承知しました。データベースは PostgreSQL にします。理由は、同時に編集する人がいることと、SQLite は書き込みが 1 つずつになることです。次は、記事のテーブルの定義を書きます。

## Previous matching Q-A exchanges (supplementary context)

### turn_id: 378a62f3-fff4-4233-9a97-1044f17bf86d saved=2026-11-22 15:59 (UTC+0900)
[user] サイトのデータベースは PostgreSQL にしましょう。複数の人が同時に編集する予定で、SQLite は書き込みのたびにファイル全体をロックするからです。
[claude] 承知しました。データベースは PostgreSQL にします。理由は、同時に編集する人がいることと、SQLite は書き込みが 1 つずつになることです。次は、記事のテーブルの定義を書きます。
```

`Top matches` は、関連度の下限を通った記録です。下限を通った記録が少ないときは、落ちた記録のうち近いものが `Possibly related` という見出しで加わります。最後の部分は、上位の記録が入っているやりとりの全体です。

## 特徴

| したいこと | N3MemoryCore がすること | 仕組み |
|---|---|---|
| 同じ説明を繰り返したくない | 発言と返答をすべて保存し、関係のあるものを毎ターン呼び出す | Codex のフック（`UserPromptSubmit`、`Stop`）。ツールの呼び出しも、手作業も要らない |
| 自分の言葉で探したい | 言い回しが違っても、関係のある過去の会話を見つける | `intfloat/multilingual-e5-base` のベクトル検索（日本語・英語・中国語・韓国語など約 100 言語）と、キーワード検索 |
| 翌日、続きから始めたい | セッションをまたいでも、プロジェクトのフォルダが違っても、記憶が残る | すべてのフォルダで 1 つの DB。今の会話の記録を先に並べる |
| データを手元に置きたい | 記憶を自分の PC のファイルに保存し、クラウドのサービスには置かない | SQLite。Codex に送られるのは、そのターンに呼び出した記憶だけで、メッセージと一緒に送られる（[詳しく](#記憶はあなたの-pc-に残ります)） |
| トークンを節約したい | 検索はローカルの埋め込みで行い（Codex のトークンは使わない）、関係のある記録だけを差し込む | 差し込む塊には上限がある（`top_matches_max`、`min_results`） |
| 複数のエージェントで 1 つの記憶を使いたい | 記録ごとに、書いたエージェントを残す | `agent_name`・`local_id`。エージェント自身の記憶を先に並べる機能は Pro 版のもの |

ほかの埋め込みモデルを使うときは、`config.json` に書いて `n3mc-free-codex --reembed` を実行します。768 次元のベクトルを出すモデルである必要があります。

## 記憶はあなたの PC に残ります

AI が覚えていてくれるのは便利ですが、その記憶がどこに置かれるのかは気になるところです。N3MemoryCore は、記憶をあなたが管理できる 1 か所、つまりあなたの PC の中のフォルダに置きます。

- **ローカルの 1 ファイル** — 記憶はすべて、SQLite のファイル `~/.n3mc-free-codex/.memory/n3memory.db` 1 つに保存されます。N3MC のアカウントも、N3MC のクラウドサービスもありません。置き場所は `N3MC_FREE_CODEX_HOME` で変えられます([オプション: データ位置の変更](#オプション-データ位置の変更))。
- **入力の原文も、その隣に残る** — `~/.n3mc-free-codex/.memory/audit.log` に、フックが受け取った原文（あなたの発言と Codex の返答。コードブロックも含む）が残ります。50 MB で入れ替わります。`n3mc-free-codex --list` には出ません。DB と同じく、他人に見せない情報として扱ってください。
- **検索は PC の中で動く** — 埋め込みモデルも検索も、手元で動きます。N3MC のサーバーは `127.0.0.1` だけで待ち受け、ほかのホスト名あての要求は断ります。同じネットワークのほかの機械からは使えません。
- **利用状況を送らない** — N3MC は利用データをどこにも送りません。コードは公開されているので、ご自身で確かめられます。


ネットワークを通るもの:

- **埋め込みモデルのダウンロード** — 最初の検索のときに、`intfloat/multilingual-e5-base`(約 1.1 GB)を Hugging Face から取得します。その後も、モデルを読み込むときに Hugging Face のライブラリが更新を確認することがあります。ダウンロードが済んだ後に `HF_HUB_OFFLINE=1` を設定すると、この確認は止まります。
- **Codex が読む部分** — そのターンに呼び出された記憶はプロンプトに加えられるので、Codex に入力した文と同じように、メッセージと一緒に OpenAI に送られます。N3MC が記憶の DB をどこかに上げることはありませんが、Codex がそのターンに使う部分は会話の一部になります。

## Free版とPro版

| | Free | Pro |
|---|---|---|
| 基本機能（保存・検索・自動の呼び出し） | ✅ | ✅ |
| 完全に同じ内容は保存しない。同じ内容の新しい版を先に並べる | ✅ | ✅ |
| 今の会話の記録を先に並べる（`b_session`） | ✅ | ✅ |
| 今のプロジェクトの記憶を優先して呼び出す | - | ✅ |
| 記憶が増えても速い検索 | - | ✅ 2 万件を超えると、メモリ上の索引で候補を絞る |
| セッションの始めに、前のセッションの続きを渡す | - | ✅ |
| 自分のエージェント・自分の環境の記憶を先に並べる（`b_local`） | - | ✅ |
| 記録の個別の削除 | - | ✅ |
| 保持期間（`--gc`） | - | ✅ 既定では無効。自分で実行する |
| インポート/エクスポート | - | ✅ データの移行・共有 |
| エンティティの索引 | - | ✅ |

どちらの版でも、記録が自動で消されたり、置き換えられたりすることはありません。

**迷ったらFree版から。** 後からPro版にアップグレードできます（Upgrade版の指示書を使用）。

## セットアップ

### Codexで指示書から生成

1. Python 3.10以上とコマンドフック対応のCodexを用意します。Codexで専用の空フォルダか、既存のFree Codex版の作業フォルダを開きます。編集可能インストールはこのフォルダのコードを使い続けます。
2. この指示書をフォルダに置き、Codexに「この指示書に従って N3MemoryCore Free Codex版を実装してください。このフォルダにコードを生成し、一時環境でテストを実行してください」と依頼します。
3. Codexは出力先を確かめて生成し、§6〜§7を一時環境で実行します。既存の作業フォルダでは依頼範囲外のファイルを保持し、既存差分を復元できる状態にします。コードだけの再生成では利用者のフックを登録しません。
4. 完全なセットアップでは、Codexが指示書の前提条件を確認し、了承済みの専用フォルダでインストールと登録を行います。

```bash
python -m pip install -e ".[test]"
n3mc-free-codex --init
```

5. 利用者はCodexの **Settings → Hooks**（CLIでは `/hooks`）でFree Codex版のフック2つを確認して信頼します。その後、Codexが指示書の§6.1〜§6.2と§7を実行し、自動保存とチャットをまたぐ検索を含む根拠を報告します。最初の意味検索では埋め込みモデルのダウンロードが必要な場合があります。

### 既存のソースからインストール

Free Codex版のリポジトリをクローンし、そのフォルダで手順4を実行します。通常インストールには `python -m pip install .` も使えます。手順5でフックを確認して信頼してください。

### データとバックアップ

`~/.n3mc-free-codex` にある `config.json` と、整合性の取れた `.memory/n3memory.db` のコピーを一緒にバックアップしてください。別のフォルダを使う場合は `N3MC_FREE_CODEX_HOME` を設定します。アンインストールするときは、先にCodexの設定から本製品のフック2つだけを取り除き、その後でパッケージをアンインストールします。データを復元する予定があればバックアップを残してください。

### 本体Free／Proの常駐サーバーへの接続

既定は単独運用です。`config.json` に `connect_server_port`（ループバックのポート）と `connect_server_root`（接続先のデータフォルダの絶対パス）の両方を設定した場合だけ、接続運用になります。既定値はいずれも `null` です。片方だけなら単独運用を続け、`connection_incomplete` の知らせを出します。両方設定した場合、または両方解除した場合は知らせを消します。検索・保存のそれぞれの直前に `GET /health` の絶対パスの `root` を `os.path.normcase(os.path.abspath(...))` で正規化し、設定と一致する相手だけを使います。接続先の `code_version` は照合しません。

確認済みの相手に検索を `POST /search`、対象の発言・応答のチャンクを `POST /buffer` で送ります。`agent_name: codex`、フックの `session_id` と `turn_id`、Codex導入環境の `local_id` を送り、`owner_id` は送らず接続先の所有者を使います。フックの `cwd` が空でない文字列なら、Gitルートのフォルダ名（取得できなければ作業フォルダ名）を `project` として送り、`cwd` がなければ省略します。Proは `project` を保存し、Freeは無視します。ローカルの監査ログは残しますが、接続運用中はローカルDBには保存しません。接続先確認・保存の失敗時もローカルDBに退避しません。発言の保存失敗は検索文脈を維持して `systemMessage` で通知し、Stopの保存失敗は非ゼロの終了コードで通知します。検索失敗は「memory search unavailable」を返しますが、別途接続先を確認した保存は続けます。

接続先の起動・停止・再起動・修復・再埋め込みは行いません。`--buffer` は同じ接続先確認と保存経路を使い、`--repair`・`--reembed` は単独運用専用です。一覧・往復全文・前後の往復はローカルDBを読みます。接続先の全文は、接続先製品のCLIでデータルートの環境変数を指定し、`--show-turn <turn_id>` または `--recall-thread <turn_id>` で読みます（Free: `python -m n3memorycore.n3memory`、`N3MC_HOME`、Pro: `python -m n3memorycore_pro.n3memory`、`N3MC_PRO_HOME`）。データは自動移行しません。

単独運用の記録を後から取り込めるよう、`--list --format jsonl` は `id`・`timestamp`・`agent_name`・`content`・`session_id`・`turn_id`・`owner_id`・`local_id` を出力します。JSONLの標準出力はオブジェクトだけとし、件数は標準エラーへ出します。取り込み時に保持するIDは受信製品の仕様なので、本物のデータを移す前に確認します。手元の現行Proの取り込みは `turn_id` を保持しますが `session_id` は保持しないため、この出力だけでは取り込み後の会話全体の再構成を保証できません。

## ID 階層構造

N3MemoryCore は 6 つの ID フィールドで各レコードの出所と文脈を識別します：

| ID | 保存場所 | 生成タイミング | 粒度 | 用途 |
|---|---|---|---|---|
| `id` (PK) | DB レコード | レコード作成時 (UUIDv7, 時系列順) | **1 レコード** | 各記憶の一意識別子 |
| `owner_id` | `config.json` | 初回起動時 (UUIDv4) | **所有者 / データフォルダ** | データの所有者識別 — 共有・マルチユーザーシナリオ・インポート由来の記録に使用 |
| `local_id` | `config.json` / API | 初回起動時 (UUIDv4)、またはリクエスト毎 | **インストール** | 1 つの Codex のインストールに 1 つ。どのセッションでも同じ値。全レコードに保存する（Free 版ではランキングには使用されない；`b_local` は Pro 機能） |
| `session_id` | Codex から渡される（フックの入力）。なければプロセスごとに作る | 会話ごと | **1 つの会話** | 同じ会話の記憶をまとめる。Free 版では `b_session` ランキングバイアス（一致=1.0、不一致=0.6）を駆動し、進行中の会話を、関係のない過去のセッションより優先する |
| `turn_id` | DB レコード | Codexのフックイベントが渡す | **1 つのやりとり** | 1 つの発言と、それに答える返答を結ぶ。`--show-turn` と `--recall-thread` に渡す |
| `agent_name` | DB レコード | 保存ごと (任意文字列) | **表示名** | 書いたものの人間可読なラベル（Codexのフックは `"codex"`）。`--buffer --agent-id <name>` はこのフィールドを入れる |

```
owner_id  (データフォルダ ~/.n3mc-free-codex と、その所有者)
  └── local_id  (インストール。どのセッションでも同じ)
        └── session_id  (Codex の 1 つの会話)
              └── turn_id  (1 つのやりとり: 1 つの発言と、その返答)
                    └── id  (1 件のレコード = 1 つのチャンク)

agent_name  (表示用のラベル。階層の外。Codexのフックは "codex")
```

## 動作環境

- **Codex**（必須）
- **Python 3.10+**
- **OS**: Windows 11・Ubuntu（動作確認済み）。macOS は対象外です

> Pythonが入っているか確認するには、ターミナルで `python --version` を実行してください。
> 未インストールの場合、セットアップ時にCodexが案内します。

## 拡張性

N3MemoryCoreは指示書（仕様書）を読ませて作るため、拡張もCodexに相談するだけで対応できます。

- **MCPサーバー化** — N3MCをMCPサーバーとして公開し、他のAIツールから記憶にアクセス
- **PostgreSQL移行** — SQLiteからPostgreSQL + pgvectorへ（1 人が 1 台の PC で使う既製の版は、PostgreSQL の N3MC Pro、`n3mc-pro-postgres`）
- **カスタム検索ロジック** — バイアス係数やランキング式の調整
- **他のembeddingモデル** — 用途に合わせたモデルへの差し替え
- **キーワード検索のトークナイザー** — 既定のキーワードの索引（FTS5 `trigram` と、日本語・中国語・韓国語のための 2 文字の索引）は、空白で区切らない言語でも、英語のような言語でも動くように選んでいます（PyPI 版はどこの国でも使われるため）。最終的なトークナイザーは、ご自分の言語・環境に合わせて直してください（例: 英語中心なら語形変化をまとめる `porter unicode61`、日本語の精度を上げるなら形態素解析）。起動のときに索引を `trigram` に作り直す確認の直しと、既存の DB の全文検索の索引の作り直しも含めて、Codex に相談すれば対応できます
- **ID階層の拡張** — `project_id`や`tag`など、分類フィールドを自由に追加
- **PDF取込** — PDFからテキストを抽出し、検索可能な記憶として保存
- **ハッシュタグ対応** — Codexが記憶に `#タグ` を自動付与して絞り込み検索（例: `--search "#AWS"`）。既存のFTSで動作し、DB変更不要

指示書をCodexに読ませて「○○を追加して」と伝えるだけです。
