## 特徴

- 💾 **ローカルに保存** — 記憶は自分の PC のファイルに保存し、クラウドのサービスには置きません。Codex に送られるのは、そのターンに呼び出した記憶だけで、メッセージと一緒に送られます([詳しく](#記憶はあなたの-pc-に残ります))
- 🔍 **意味で検索** — キーワードが違っても、関連する過去の会話を引き出します。デフォルトで多言語対応（`intfloat/multilingual-e5-base`）— 複数言語の検索に対応しますが、精度は質問と保存内容によって異なります。モデル変更時は次元の確認と再埋め込みが必要で、設定の変更だけでは既存の索引と互換になりません
- 🔄 **セッションをまたいで記憶** — 翌日開いても、先週の続きから話せます
- ⚡ **自動で動く** — フックの登録・信頼・動作確認後は、質問と最終回答の保存、過去の履歴の検索を自動で行います。保存拒否や検出した資格情報は除外し、コードブロックは `[code omitted]` に置き換えます。画像の保管は対象外です
- 🤖 **マルチエージェント対応** — 複数のAIエージェントが1つの記憶DBを共有できます。記録ごとに書いたエージェント（`agent_name`・`local_id`）が残ります。これらは出所情報であり、認証やアクセス制御ではありません
- 🔗 **ローカルデータの持ち運び** — SQLiteのDBと設定を合わせてバックアップできます。実装間の移行ではスキーマと埋め込みモデルの互換性を確認してください。異なる版のDBを自動で統合できるという保証はありません。
- 💬 **繰り返しの説明を減らす** — 関連する過去の情報を使って作業を再開できます。埋め込み計算はローカルですが、差し込む記憶はCodexの入力コンテキストを使うため、総トークン消費の削減を一律には保証しません。

## 仕組み

```text
ユーザーの質問
    → UserPromptSubmit：過去の記録を検索し、質問を保存
    → 関連する履歴をCodexへ渡す
    → Codexが回答
    → Stop：同じturn_idで最終回答を保存
```

自動保存には、利用するCodex環境で両フックが信頼・有効化されている必要があります。検索結果には不足や無関係な情報が含まれることがあるため、現在の事実として扱う前に根拠を確認します。

### AGENTS.md と検索記憶

`AGENTS.md` には作業時に常に守る指示を書きます。N3MemoryCore は過去の会話を検索し、その質問に関係する履歴をフックの標準出力で渡します。検索結果は履歴データであり、新しい指示ではありません。

## 記憶はあなたの PC に残ります

AI が覚えていてくれるのは便利ですが、その記憶がどこに置かれるのかは気になるところです。N3MemoryCore は、記憶をあなたが管理できる 1 か所、つまりあなたの PC の中のファイルに置きます。

- **ローカルの 1 ファイル** — 記憶はすべて、SQLite のファイル `~/.n3mc/.memory/n3memory.db` 1 つに保存されます。N3MC のアカウントも、N3MC のクラウドサービスもありません。置き場所は `N3MC_HOME` で変えられます([オプション: データ位置の変更](#オプション-データ位置の変更))。
- **検索は PC の中で動く** — 埋め込みモデルも検索も、手元で動きます。N3MC のサーバーは `127.0.0.1` だけで待ち受け、ほかのホスト名あての要求は断ります。同じネットワークのほかの機械からは使えません。
- **利用状況を送らない** — N3MC は利用データをどこにも送りません。コードは公開されているので、ご自身で確かめられます。
- **中身を見られる・消せる** — `n3mc --list` で保存された内容を表示できます。削除は[アンインストール](#アンインストール)、保存中のデータを含めた保管は[バックアップと復元](#バックアップと復元)を参照してください。

ネットワークを通るもの:

- **埋め込みモデルのダウンロード** — 初回のモデル読込み時に、`intfloat/multilingual-e5-base`を Hugging Face から取得します。その後も、モデルを読み込むときに Hugging Face のライブラリが更新を確認することがあります。ダウンロードが済んだ後に `HF_HUB_OFFLINE=1` を設定すると、この確認は止まります。
- **Codex が読む部分** — そのターンに呼び出された記憶はプロンプトに加えられ、Codex の会話処理先に送られます。N3MC が記憶の DB 全体をアップロードすることはありませんが、呼び出された部分は会話の一部になります。

## セットアップ

導入経路は以下の 2 通りをサポートします。お好みのスタイルでお選びください。

### 経路 A — AI ネイティブセットアップ（プロジェクト本来のフロー）

1. 専用の空フォルダーを用意し、そこでCodexを開きます。導入後もフックからコードを使うため、このフォルダーは残します。
2. 上の表から日英どちらかの指示書を取得し、Codexに読み込ませます。
3. 次のように依頼します。「この指示書に従ってN3MemoryCoreを実装してください。GPUは使用せずCPUで動作させてください。インストール先を確認し、既存設定を保持して、確認できた項目と私の操作が必要な項目を報告してください。」
4. 実装・確認のあとCodexを再起動し、フックの内容を確認して信頼・有効化します。その後、新しいチャットで複数ターンの動作を確認します。

指示書でも、**経路Aを指示書からの実装、経路Bを参考コードの直接利用**としています。所要時間は環境・依存関係・モデル取得により異なります。生成された実装は個別に検証してください。参考コードのテスト結果だけでは、生成した実装の動作確認にはなりません。

Hyper-V仮想マシンで、指示書を使ったCodexによるコード生成を利用者が確認しました。利用者の報告によると、付録の手動確認①データフロー、②CLI仕様との比較、③`--buffer`で保存して別セッションの`--search`で取得する試験も通過しています。フックの信頼状態と、新しいチャットでの自動保存・自動想起は別途確認する項目です。

### 両経路共通：Codexでフックを信頼・有効化する

`--init` または指示書からの実装で `~/.codex/hooks.json` に登録されても、Codexでの信頼・有効化は別の操作です。登録後は次の順番で確認してください。

1. `~/.codex/hooks.json` の `UserPromptSubmit` と `Stop` を開き、実行するPythonのパスと `n3memorycore.codex_entry --prompt` / `--stop` が意図したものか確認します。生成コードの場合は、生成されたコマンドに読み替えます。
2. Codexを終了して再起動します。Hyper-Vでの導入時は、再起動してから新しいフックを承認できました。
3. Codexのチャットで `/hooks` を開き、**UserPromptSubmitとStopの両方**について、表示されたコマンドを確認して信頼・有効化します。一方だけでは質問と回答を一組として保存できません。
4. 新しいチャットを開き、短い架空の合言葉を伝えます。回答後に `--list` で質問と回答を確認し、別の新しいチャットで合言葉を尋ねます。

`hooks.json` に2件あること、手動の `--buffer` / `--search` が成功することだけでは、Codexがフックを実行した証拠にはなりません。

### 経路 B — 参考コードをインストールする

この経路では、本リポジトリのコードを使います。指示書からの実装テストにはなりません。

#### 1. インストール

専用のPython仮想環境を使います。配布設定の名前は現在も従来版と同じ `n3memorycore-free` なので、同じ仮想環境へ両方を入れないでください。従来版のPyPIコマンドは、このCodex版の導入経路として案内しません。

Windows PowerShell:

```powershell
git clone https://github.com/NeuralNexusNote/n3mc-free-codex.git
cd n3mc-free-codex
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\python.exe -m n3memorycore.n3memory --init
```

以降の例の `python` は、この仮想環境の実行ファイルを指します。Windowsでは `.\.venv\Scripts\python.exe` を使ってください。フック登録後に仮想環境を削除・移動しないでください。

要件はPython 3.10以上と両フックに対応するCodex環境です。参考コードのモデルはCPUで動作します。依存関係とモデルの初回取得には、ネットワーク・ディスク容量・時間が必要です。取得後はキャッシュを利用できます。

#### 2. Codex に接続する

```bash
python -m n3memorycore.n3memory --init
```

`~/.n3mc/` に設定と DB 用のフォルダを用意し、ユーザー全体の `~/.codex/hooks.json` に UserPromptSubmit と Stop のコマンドを登録します。既存の他のフックは保持し、変更前にバックアップを作ります。登録するコマンドはインストールに使用した Python の絶対パスを使います。上の「両経路共通」の順序でCodexを再起動してから、`/hooks` で両コマンドを信頼・有効化してください。

#### 3. フック登録を検証する

`~/.codex/hooks.json` の UserPromptSubmit と Stop に `n3memorycore.codex_entry` が各 1 件あることを確認します。さらに `/hooks` で両方が信頼され、有効になっていることを確認します。JSON の登録だけでは自動捕捉の成功は確認できません。

#### 4. 新しいチャットを開く

フックの信頼・有効化後に新しいCodexチャットを開いてください。`hooks.json` の存在だけで判断せず、質問・Stopが実際に動いたことを確認してください。

#### 5. 動作確認

新しい Codex セッションで何かメッセージを送信し、Codex が応答したあと以下を実行:

```bash
python -m n3memorycore.n3memory --list
```

最低 2 件のレコードが表示されるはずです — `[user]` プレフィックス（あなたのメッセージ）と `[claude]` プレフィックス（Codex の応答）。`[claude]` は互換性のために残した旧ラベルで、この版ではCodexの回答を表します。続けて別チャットで想起を確認します。保存されない場合は下の **トラブルシューティング** を確認してください。

#### オプション: データ位置の変更

`N3MC_HOME=/path/to/dir` を設定するとデータ保存先を変更できます。この値は実行時に読み取られ、`--init` では永続化されません。CLI と Codex のフックを起動する環境の両方で同じ値を設定してください。

### トラブルシューティング（両経路共通）

保存されない場合は、Codex の `/hooks` で両フックの信頼・有効状態を確認し、新しいチャットを開いてください。フック失敗は stderr に表示されます。`~/.n3mc/.memory/server.log` と `audit.log` も確認してください。モデルの取得が必要な場合はネットワーク接続を確認します。

### セットアップ後の体験

フックの信頼確認と複数ターンの試験が通ったあと：
- あなたの発言に関連する過去の会話が、自動で検索・注入されます
- Codexは関連する履歴を回答に利用できます。ただし過去の全情報が毎回取得される保証はありません
- 保存も検索もバックグラウンドで行われるため、操作は不要です

### 記憶の呼び出しの調整（vector_min_cos）

N3MC は、質問と意味の近い記録をベクトル検索で探します。`vector_min_cos` は、
「どれくらい近ければ候補にするか」のしきい値です（既定 0.85）。

| 値を | 起きること |
|---|---|
| 下げる（例 0.80〜0.83） | 言い回しが違っても拾いやすくなる。短い質問でも記録が出やすい。その分、関係の薄い記録も混ざり、差し込みが長くなる |
| 上げる（例 0.88） | 関係の薄い記録が減り、差し込みが短くなる。その分、関係のある記録も落ちやすい |

目安は 0.80〜0.88 です。値は `~/.n3mc/config.json` に `"vector_min_cos": 0.83` のように書きます。
保存すると、次の質問から効きます（サーバーは自動で起動し直します）。
書き間違えて読めないときは、ファイルはそのまま残り、直すまで既定値で動きます。そのことは、記憶の差し込みの先頭に 1 日 1 回表示されます。数値は引用符を付けずに書いてください。

### 弱い候補（min_results）

v1.9.0指示書の既定値は `min_results=3` です。関連度の下限を通った候補が少ない場合、落ちた候補から補充し、`## Possibly related (weak matches — may be unrelated)` に分けて表示します。補充可能な候補がなければ結果は空のままです。

現在の参考コードは `min_results=0` が既定値で、弱い候補を強制補充しません。既存 `config.json` に3などを明示している場合は、その値が維持されます。補充を止めるには `"min_results": 0` とします。しきい値を下げたり候補を増やしたりすると、関連情報を拾いやすくなる一方、無関係な情報も増えます。

古さだけを理由に記録を検索から除外しません。参考コードでは、明示的に訂正元・忘却対象にしたターンは通常検索から除外します。

### バックアップと復元

SQLite は WAL モードのため、稼働中の `n3memory.db` だけをコピーすると直近の保存が欠ける場合があります。[バックアップ手順](docs/BACKUP.md)の SQLite backup API で整合した DB を作り、`config.json` と一緒に保管してください。`owner_id`・`local_id` は出所を識別する ID で、認証鍵ではありません。

### アンインストール

Codex に N3MemoryCore の削除を依頼し、先に `~/.n3mc/` のバックアップを確認してください。フック登録と Python 環境を解除したあと、保存済みの DB を残すか削除するかを決めてください。

## ID 階層構造

以下は出所を表すフィールドです。このほかにCodexから受け取る `turn_id` で1往復の質問・最終回答を対応付けます。レコード単位の `id` とは異なります。

| ID | 保存場所 | 生成タイミング | 粒度 | 用途 |
|---|---|---|---|---|
| `id` (PK) | DB レコード | レコード作成時 (UUIDv7, 時系列順) | **1 レコード** | 各記憶の一意識別子 — 削除・重複検出に使用 |
| `owner_id` | `config.json` | 初回起動時 (UUIDv4) | **所有者 / N3MC サーバー** | データの所有者識別 — 共有・マルチユーザーシナリオ・インポート由来の記録に使用 |
| `session_id` | メモリ内またはホストから供給 | Codexの `thread_id` を受け取る | **タスク／プロジェクト／会話** | 同じタスク・プロジェクト・会話に属する記憶をまとめて浮上させる。Free 版では `b_session` ランキングバイアス（一致=1.0、不一致=0.6）を駆動し、進行中の会話を関連無関係なセッションより優先する |
| `local_id` (agent_id) | `config.json` / API | 初回起動時 (UUIDv4)、またはリクエスト毎 | **エージェント / インストール** | 発話エージェントの UUIDv4 識別子。マルチエージェント時は各エージェント固有の UUID を指定（Free 版ではレコードに保存されるがランキングには使用されない；`b_local` は Pro 機能） |
| `agent_name` | DB レコード | バッファ呼び出し時 (任意文字列) | **エージェント表示名** | エージェントの人間可読なラベル（例：`"codex"`） |

```
owner_id  (1 つの N3MC サーバ／データ所有者)
  └── session_id  (1 つのタスク／プロジェクト／会話)
        └── local_id  (そのセッション内で発話するエージェント)
              ├── agent_name  (その表示名: "codex" 等)
              └── id  (1 件の記憶レコード)
```

## 拡張性

N3MemoryCoreは指示書（仕様書）を読ませて作るため、拡張もCodexに相談するだけで対応できます。

- **MCPサーバー化** — N3MCをMCPサーバーとして公開し、他のAIツールから記憶にアクセス
- **PostgreSQL移行** — SQLiteからPostgreSQL + pgvectorへ。チーム規模の運用に
- **カスタム検索ロジック** — バイアス係数やランキング式の調整
- **他のembeddingモデル** — 用途に合わせたモデルへの差し替え
- **キーワード検索のトークナイザー** — 既定の FTS5 `trigram` は、日本語・中国語のように空白で区切らない言語でも、英語のような言語でも動くように選んでいます（複数言語の会話を対象にするため）。最終的なトークナイザーは、ご自分の言語・環境に合わせて直してください（例: 英語中心なら語形変化をまとめる `porter unicode61`、日本語の精度を上げるなら形態素解析）。既存の DB の作り直しも含めて、Codex に相談すれば対応できます
- **ID階層の拡張** — `project_id`や`tag`など、分類フィールドを自由に追加
- **PDF取込** — PDFからテキストを抽出し、検索可能な記憶として保存
- **ハッシュタグ対応** — Codexが記憶に `#タグ` を自動付与して絞り込み検索（例: `--search "#AWS"`）。既存のFTSで動作し、DB変更不要

これらはカスタマイズの例であり、この版の標準搭載機能ではありません。指示書をCodexに読ませて変更内容を伝え、生成された実装を検証してください。
