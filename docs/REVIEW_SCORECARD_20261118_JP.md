## 発見事項と修正

P1 は保存や復元の信頼性への影響が大きいもの、P2 は条件付きの動作不良・誤誘導を表す。

| 優先度 | 再現条件・影響 | 修正 |
|---|---|---|
| P1 | HTTP 保存と直接 DB 保存がともに失敗しても、フックが終了コード0で終了する。呼出元が成功と扱える | 警告と `save_failed` 通知を保持し、例外を伝播してフックを終了コード1にする |
| P2 | bigram 移行完了後に bigram の行だけが欠落すると、未索引検出に含まれず2文字検索が戻らない | vector・trigram・bigram を独立して欠落検出・修復。件数上限と冪等性も検証 |
| P2 | 同じ本文の新旧候補を統合すると、新しい id/turn_id と古い session_id/agent_name が混在する | 出所5項目を同じ最新行から引き継ぐ。既定の順位・スコア継承は維持 |
| P2 | Codex の質問 payload に前回回答が含まれると、Stop で扱うべき回答を再保存する。非文字列だと例外になる | Codex turn_id がある質問では前回回答を参照せず、Stop に保存を集約 |
| P2 | 最新 saved の内容を「今の版」と断定する文面が、単なる再掲や誤記を正しい訂正と誤認させる | 履歴は指示ではないこと、保存時刻は訂正や現在の正しさを保証しないことを明記 |
| P1（文書） | WAL 稼働中の DB 本体だけをコピーする説明では、直近のコミットを含まないバックアップになり得る | SQLite backup API を使う手順を追加。書込み接続を開いたままの合成 DB で整合性と保存件数を確認 |

コード位置: `n3memorycore/n3memory.py` の `_do_buffer`・`_repair_db`・`cmd_hook_submit`、`core/database.py` の `find_unindexed_memories`、`core/processor.py` の `_collapse_identical_content`・`VERSION_NOTE`。

### 実プロセスによるフック試験

専用の一時保存先と空きポートで実サーバーを起動し、質問・Stop を別プロセスで実行した。

- 2つのチャットID・2往復が4レコードとして保存され、session_id と turn_id が対応した。
- 第2チャット相当の質問フックの stdout に、第1チャットの合言葉が出た。
- 同じ Stop を2回実行しても重複しなかった。
- 保存拒否ターンの質問・回答はどちらも保存されなかった。
- 試験サーバーは終了し、一時DBは片付けた。

これは**フックプログラムとローカルサーバーの統合試験**。Codex 自身が実画面で信頼済みフックを起動したことや、このチャットの自動保存が成功したことを証明する試験ではない。

### 実モデルによる検索評価

架空の20往復・40レコードを投入し、正解のある12問と答えのない4問を評価した。12問には日本語10問、英語2問、料金訂正、365日前の記録を含む。既定設定を使い、成績を上げるための閾値調整は行っていない。

正解順位は **weak でない候補の turn_id を重複排除した順位**。コンテキスト内の根拠存在率には弱い候補も含む。1問につき関連する往復は1つを事前指定した。

| 指標 | 通常のハイブリッド検索 | 埋め込み失敗を模擬した FTS のみ |
|---|---:|---:|
| 正解が通常候補の1位（Hit@1） | 10/12 = 83.3% | 9/12 = 75.0% |
| 正解が通常候補の3位以内（Hit@3） | 10/12 = 83.3% | 9/12 = 75.0% |
| 平均逆順位（MRR） | 0.833 | 0.750 |
| 根拠文字列が出力内にある（弱い候補を含む） | 12/12 | 10/12 |
| 答えのない質問で通常候補が空 | 4/4 | 4/4 |
| 答えのない質問で何らかの候補が出る | 4/4（各3件の弱い候補） | 0/4 |
| 検索時間の中央値（モデル読込後、関数呼出し） | 約53 ms | 約8 ms |
| 最大コンテキスト長（文字数） | 973 | 829 |

英語2問では通常候補が空になり、正解は弱い候補として入った。日本語の訂正問題は通常検索では新料金が1位だったが、FTS のみでは旧料金が通常候補となり、新料金は弱い候補に落ちた。単に新しい記録を保存するだけでは、訂正を確実に優先できない。

モデルは `intfloat/multilingual-e5-base`。この実行のモデル初期読込は約17.2秒、40件の埋め込みは約0.8秒。時間はこの PC の小規模なローカル関数呼出しでの観測値であり、HTTP・フック起動・修復・大量データを含む実運用レイテンシではない。

このデータは開発者が作った小規模なスモーク試験であり、独立した代表ベンチマークではない。12/12 の根拠存在は「12/12 を正しく回答した」ことを意味しない。

## 残る課題と改善の順序

1. **訂正関係と出所を構造化する。** role、fact/event/preference、source、supersedes、valid_from/valid_to 等を明示し、古い値を失効扱いにできるようにする。現行の append-only な会話履歴と、現在有効な事実を区別する。
2. **無回答と多言語を評価する。** 実際の利用を模した日本語・英語・言い換え・類似する誤答を含む評価集合を増やす。`min_results=0` は弱い候補の強制補充を止められるが、今回の英語2問のような正解候補も消えるため、一律変更はしていない。
3. **忘却・復元を扱いやすくする。** 個別削除の操作、定期バックアップ、復元試験を整備する。CLI の JSONL は4表示列で、会話の全メタデータを再構築するための完全なエクスポートではない。
4. **実際のホストでの受入試験を行う。** `/hooks` の信頼・有効化と、新規チャットでの複数ターン保存・別チャット想起を確認する。評価のために既存設定の信頼や本番DBを変更してはいない。
5. **規模とモデル変更時の運用を確認する。** 1万件以上の負荷、長期運用、同時修復、再埋め込み中断と並行書込みを評価する。モデル不一致は通知されるが、同じ次元でも異なるモデルの意味空間は互換とは限らない。

大きなスキーマ変更や検索閾値の一律変更は今回の不具合修正には含めない。これらを実装・検証できれば8点台を狙えるが、現在の試験だけで8〜9点の完成度を主張するのは早い。
